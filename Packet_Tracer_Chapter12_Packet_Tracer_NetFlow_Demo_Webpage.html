NetFlow Monitoring with Cisco Packet Tracer

Cisco Packet Tracer 9.x • Estimated time: 35–50 minutes • Demo, not a graded assignment

Traffic analysisNetFlow v9Cisco IOS
Purpose. Configure a Cisco router to summarize network conversations as flow records and export them to a NetFlow Collector. Generate ping and HTTP traffic, then compare the results.

1. Learning objectives

  1. Describe NetFlow exporter, collector, and flow record.
  2. Configure IP addressing and routing across two subnets.
  3. Enable traditional NetFlow monitoring on a router interface.
  4. Export NetFlow v9 data to a collector on UDP port 9996.
  5. Generate traffic and interpret protocol, IP address, port, and packet-count information.
  6. Explain why one two-way conversation may produce separate unidirectional flow records.

2. How NetFlow works

A flow groups packets with common attributes, conventionally including source and destination IP addresses, source and destination transport ports, IP protocol, interface, and other attributes. The exporter counts packets and bytes and periodically sends flow information to a collector. NetFlow reports traffic metadata, not full application payloads.

Logical topology. Use S2, an optional second 2960 switch, to connect the two servers to R1 G0/1; the right-side branching lines represent this shared LAN.

Required Packet Tracer devices

  • 1 Cisco 2911 ISR router (R1)
  • 2 Cisco 2960 switches (S1 for client LAN; S2 for server LAN)
  • 1 PC (PC0)
  • 2 Server-PT devices (Collector and Web Server)
  • 5 copper straight-through cables

Physical links: PC0 Fa0 → S1 Fa0/1; S1 Fa0/24 → R1 G0/0; R1 G0/1 → S2 Fa0/24; Collector Fa0 → S2 Fa0/1; Web Server Fa0 → S2 Fa0/2.

3. Configure R1 interfaces

Click R1 → CLI; enter:

enable
configure terminal
hostname R1
interface gigabitEthernet0/0
 description CLIENT-LAN
 ip address 192.168.10.1 255.255.255.0
 no shutdown
exit
interface gigabitEthernet0/1
 description SERVER-LAN
 ip address 192.168.20.1 255.255.255.0
 no shutdown
exit
end
show ip interface brief

Both GigabitEthernet interfaces should display up/up after cabling and convergence. Both subnets are directly connected; no static routes are needed.

4. Configure PC and servers

  1. Open PC0 → Desktop → IP Configuration. Enter its IP, mask 255.255.255.0, and gateway from the table.
  2. Set the Collector IP and gateway in Desktop → IP Configuration.
  3. Set the Web Server IP and gateway in Desktop → IP Configuration.
  4. On the Web Server, open Services → HTTP and ensure HTTP On.
  5. From PC0 → Desktop → Command Prompt, test connectivity:
ping 192.168.10.1
ping 192.168.20.1
ping 192.168.20.10
ping 192.168.20.20

Verify connectivity before turning on flow monitoring. A first ping may time out during ARP resolution.

5. Start the NetFlow collector

  1. Open the Collector server.
  2. Select Desktop → NetFlow Collector (in versions where this is the application location).
  3. Choose On to enable the collector. It should listen on the Packet Tracer collector port, UDP 9996.
  4. Leave the collector window available so you can observe flow information after traffic is generated.
Version note: Cisco has documented the NetFlow Collector as a Packet Tracer server desktop application. If your 9.x build places it elsewhere, look for the same named application. If your server model has no NetFlow Collector, try the standard Server-PT device and verify availability before proceeding.

6. Configure NetFlow on R1

Enable traditional ingress NetFlow on the client-facing router interface and export NetFlow v9 records to the collector.

enable
configure terminal
interface gigabitEthernet0/0
 ip flow ingress
exit
ip flow-export destination 192.168.20.10 9996
ip flow-export version 9
end
write memory

Command explanations:

CommandPurpose
ip flow ingressObserve packets arriving on G0/0.
ip flow-export destination 192.168.20.10 9996Identify the collector IP and UDP destination port.
ip flow-export version 9Use the NetFlow v9 export format.
Why monitor G0/0? PC0 → Web Server traffic enters R1 via G0/0, so its forward flows can be counted there. The reverse traffic from Web Server → PC0 enters via G0/1 instead; the optional bidirectional step below adds ingress monitoring on G0/1.

7. Generate traffic

Test A: ICMP

  1. On PC0 → Desktop → Command Prompt, run:
ping 192.168.20.20
  1. Run the ping a few times if needed to create enough traffic.
  2. On R1 CLI, run show ip cache flow.
  3. Open the NetFlow Collector and check whether new flows appear. Use Realtime mode and allow simulation time for export/aging if no records are yet displayed.

Test B: HTTP

  1. On PC0 → Desktop → Web Browser, visit http://192.168.20.20.
  2. Reload the page several times.
  3. Return to R1 and run show ip cache flow.
  4. Examine the collector application again. Look for a TCP flow with destination port 80.

ICMP uses IP protocol number 1. TCP uses IP protocol number 6. Actual flow counts and timing depend on the simulation.

8. Verify and interpret the flow cache

Use these commands in privileged EXEC mode:

show ip flow interface
show ip cache flow
show running-config

Illustrative flow-cache format (not a promised exact Packet Tracer output):

SrcIf  SrcIPaddress    DstIf  DstIPaddress   Pr  SrcP DstP  Pkts
Gi0/0  192.168.10.10   Gi0/1  192.168.20.20  01  0000 0000   4
Gi0/0  192.168.10.10   Gi0/1  192.168.20.20  06  C350 0050   7

In this example, 01 represents ICMP and 06 represents TCP. Port numbers in this IOS display are hexadecimal: 0050 is TCP port 80; C350 represents an example ephemeral source port (50000 decimal). The exact values change between sessions.

9. Optional: observe both directions

To record return traffic arriving from the server subnet, enable ingress NetFlow on R1 G0/1 as well:

enable
configure terminal
interface gigabitEthernet0/1
 ip flow ingress
end
show ip flow interface

Repeat the HTTP test. Look for at least one flow from 192.168.10.10 to 192.168.20.20 and another flow in the reverse direction. NetFlow records are directional: a bidirectional TCP connection is generally represented by separate forward and reverse flows.

10. Optional: inspect export traffic in Simulation Mode

  1. Switch from Realtime to Simulation.
  2. Open Edit Filters, and select UDP or NetFlow if your build provides a specific NetFlow filter.
  3. Generate another HTTP request and advance events with Capture/Forward or Auto Capture/Play.
  4. Look for UDP traffic addressed to 192.168.20.10 with destination port 9996.
Limitation: Not all Packet Tracer versions expose exported NetFlow packets as inspectable simulation PDUs, and export may not occur immediately because of flow-cache timeouts. The show ip cache flow command and the NetFlow Collector application are the primary checks.

11. Troubleshooting

SymptomCheck
Pings failVerify cabling, IP mask, default gateways, and show ip interface brief.
ip flow ingress rejectedVerify that you used a supported ISR router and correct interface. Packet Tracer device IOS command coverage varies.
No flow cache entriesGenerate traffic routed through R1, not just traffic within one switched subnet. Confirm NetFlow is enabled on the ingress interface.
Cache entries exist but collector emptyConfirm the collector is On; IP 192.168.20.10; export version 9; UDP port 9996; give flows time to expire/export.
Only PC-to-server flows appearNormal if ingress monitoring is enabled only on G0/0. Add ingress NetFlow on G0/1 for the reverse direction.
NetFlow Collector app missingUse Server-PT and confirm the application exists in your Packet Tracer build. A physical IOS router or other emulator may be necessary if unsupported.

12. Demo verification checklist

  • All endpoints can ping their default gateway.
  • PC0 can ping Web Server and Collector across subnets.
  • The Web Server responds to an HTTP browser request.
  • R1 accepts ip flow ingress and exporter configuration.
  • show ip cache flow displays traffic counters or entries after generating traffic.
  • NetFlow Collector receives and displays exported records, if supported.
  • Students can explain the difference between a flow and a full packet capture.

13. Discussion questions

  1. What is the difference between a NetFlow exporter and a collector?
  2. Why is a NetFlow record not the same as a packet capture?
  3. Which fields distinguish an HTTP flow from an ICMP flow?
  4. Why do ping and HTTP generate different flow types?
  5. Why might enabling monitoring only on G0/0 miss return traffic?
  6. What is the purpose of UDP destination port 9996?
  7. How can NetFlow help identify unusually heavy traffic or unexpected communication?

14. Instructor demonstration wrap-up

Key point: NetFlow summarizes who communicated with whom, using which protocol and ports, and how much traffic moved. In this lab, the router observes traffic, maintains a flow cache, and exports flow records to a separate collector for analysis.

Demo success = valid routed traffic + router flow-cache evidence + collector records (when supported). NetFlow export timing, chart appearance, and cache counts are not fixed.
