1. Lab Purpose

Use a small, functioning network to connect risk decisions with observable outcomes. Students identify assets and dependencies, prioritize plausible risks, apply a limited set of controls, and verify that service can be restored after a controlled fault.

  • Distinguish assets, threats, vulnerabilities, likelihood, impact, and residual risk.
  • Build a simple risk register and select justified treatments.
  • Reduce exposure from unused switch ports and unexpected device replacement.
  • Observe the availability tradeoff introduced by a shutdown-mode control.
  • Save a known-good baseline and practice a documented rollback.
  • Separate network reachability from DNS and application health.
Instructor note: This is an original live demonstration, not a graded assignment. The risk discussion drives the technical steps; the controls are examples, not a complete security design.
Simulation scope: Packet Tracer can model selected network configurations and failures. It does not establish real-world likelihood, perform a vulnerability assessment, validate regulatory compliance, or simulate a full incident investigation. Physical security, patching, malware protection, business continuity, and organizational policy are discussion topics here.

2. Lab Scenario

Northstar Training Center depends on a staff portal hosted on a separate services network. An equipment review finds unused active switch ports, no documented recovery checkpoint, and several single points of failure. The instructor acts as network administrator; students help explain and prioritize the risks.

Learning Objectives

  • Inventory the portal, DNS, endpoint, switching, and gateway dependencies.
  • Explain confidentiality, integrity, and availability impacts.
  • Assign illustrative likelihood and impact scores, then explain their limitations.
  • Apply and verify a preventive control and a corrective recovery procedure.
  • Document control side effects and remaining exposure.
  • Choose mitigation, avoidance, transfer, or acceptance with an accountable owner.

Risk Scoring for This Exercise

Use likelihood 1–3 (low, medium, high) and impact 1–3 (minor, material, severe). Multiply them for a classroom priority score. Treat 1–2 as low, 3–4 as medium, and 6–9 as high. These are illustrative teaching judgments, not measured probabilities or a standardized assessment.

Discuss the highest scores first, but also consider control cost, feasibility, dependencies, and business priorities. After testing, revisit scores with explicit assumptions; do not automatically mark a risk eliminated.

6. Verify Normal Operations

Part G — Infrastructure Checks

On RTR-HQ-01:

show ip interface brief
show ip route

Both used interfaces should be up/up, with connected routes for both /24 networks. On each switch, inspect show interfaces status and confirm the cabled ports are connected.

Part H — Client and Service Checks

On PC-STAFF-01, open Command Prompt:

ipconfig
ping 192.168.100.22
ping 192.168.100.1
ping 192.168.101.10
ping portal.northstar.com

Repeat an initial ping if ARP resolution causes a first-packet timeout. On both staff PCs, open the Web Browser and test:

http://192.168.101.10
http://portal.northstar.com

Both should display the portal. Record these results before applying controls.

Part I — Inspect the Dependency Path

  1. Switch to Simulation Mode and filter ARP, ICMP, DNS, TCP, and HTTP.
  2. Generate a new portal request and step through Capture/Forward.
  3. Identify the DNS exchange, gateway forwarding, and HTTP traffic.
  4. Ask which assets must remain available and which traffic is not encrypted.
  5. Return to Realtime before changing configurations.

Cached ARP and DNS entries can hide fresh lookup events. Restart a client in a saved working copy if needed; clearing the event list alone does not necessarily clear caches.

7. Risk Treatment Demonstrations

Part J — R1: Disable Unused Ports

Before treatment, connect PC-TEST-01 to SW-STAFF-01 Fa0/10 using a straight-through cable and ping the server. With the correct static configuration it should succeed, illustrating the exposure. Disconnect the test PC.

On SW-STAFF-01:

enable
configure terminal
interface range fastEthernet0/3 - 24
 description UNUSED - administratively disabled
 shutdown
 exit
interface gigabitEthernet0/2
 description UNUSED - administratively disabled
 shutdown
 exit
end

On SW-SERVICES-01:

enable
configure terminal
interface range fastEthernet0/2 - 24
 description UNUSED - administratively disabled
 shutdown
 exit
interface gigabitEthernet0/2
 description UNUSED - administratively disabled
 shutdown
 exit
end

Reconnect PC-TEST-01 to staff Fa0/10. Its link and server access should fail. Confirm with show interfaces fastEthernet0/10 that the port is administratively down. Verify both approved PCs still reach the portal, then disconnect the test PC again.

Scope check: Staff Fa0/1, Fa0/2, and G0/1 and services Fa0/1 and G0/1 remain enabled. Never apply the unused-port ranges blindly to a differently cabled topology.

Part K — R2: Learn One Approved Endpoint

Ensure the original PC-STAFF-01 is connected to staff Fa0/1 before enabling learning. On SW-STAFF-01:

configure terminal
interface fastEthernet0/1
 switchport mode access
 switchport port-security
 switchport port-security maximum 1
 switchport port-security violation shutdown
 switchport port-security mac-address sticky
end

From PC-STAFF-01, ping its gateway to generate traffic. Then inspect:

show port-security interface fastEthernet0/1
show port-security address
show running-config

Confirm Fa0/1 has learned the actual approved PC's MAC, the maximum is one, and the port is secure-up. Do not proceed with the replacement test before verifying the learned address.

Part L — Test and Recover from a Violation

  1. Disconnect PC-STAFF-01 from Fa0/1.
  2. Connect PC-TEST-01 to that same port and generate a ping to 192.168.100.1. It has a different MAC address and its own .99 IP.
  3. Inspect show port-security interface fastEthernet0/1. Expect a violation and secure-shutdown/err-disabled state; exact display varies by version.
  4. Confirm PC-STAFF-02 still reaches the portal. The control's effect is limited to the protected port in this scenario.
  5. Disconnect the test PC and reconnect the original approved PC before recovering the port.

Recover on SW-STAFF-01:

configure terminal
interface fastEthernet0/1
 shutdown
 no shutdown
end

Wait for the link to recover. Verify secure-up and successful gateway/server/portal tests. Retain the original sticky MAC; do not remove the binding merely to allow the test endpoint.

Control tradeoff: This reduces casual device replacement but is not user authentication, malware detection, or protection against MAC impersonation. A legitimate device replacement can also trigger shutdown. Only Fa0/1 is protected in this example; Fa0/2 still represents residual exposure.

Part M — Save and Reassess

With approved clients working and the test PC disconnected, run copy running-config startup-config on both switches. Saving after learning retains the sticky MAC in startup configuration. Save the project as Chapter10_Risk_Controlled.pkt, then create another working copy for incident practice.

Revisit R1 and R2: explain how the tested controls reduce the specific exposure, identify what they do not address, and assign any revised score as a classroom judgment. R4 remains unresolved: no redundant server, switch, or gateway was added.

8. Incident and Recovery Demonstrations

Workflow: Record the symptom and time, determine scope, inspect evidence, make one justified change, validate recovery, and update the record. Use a working copy and introduce only one fault at a time.

Demo 1 — R3: Accidental Server-Port Shutdown

On SW-SERVICES-01:

enable
configure terminal
interface fastEthernet0/1
 shutdown
end

Both staff PCs lose server ping, fresh DNS resolution, and portal access. They should still reach each other and the staff gateway. Inspect the server link and show interfaces fastEthernet0/1. The administrative state points to a configuration change.

Roll back the change on SW-SERVICES-01:

configure terminal
interface fastEthernet0/1
 no shutdown
end

Wait for recovery, then retest server IP, DNS, and HTTP from both clients. Record actual time to restore for classroom comparison, not as proof of a production recovery commitment.

Demo 2 — Reachable Host, Failed Application

On SRV-HQ-01 turn Services > HTTP Off. Server ping should still work, but a fresh HTTP request should fail. Restore HTTP On and request the page again. A page already visible in the browser is not evidence of current availability.

Demo 3 — DNS Configuration Error

Change PC-STAFF-01's DNS to unused 192.168.101.99. Direct-IP HTTP should still work. To avoid cached answers, add a new A record on the server: riskcheck.northstar.com → 192.168.101.10, and request that new name from the PC. Restore client DNS to 192.168.101.10 and retest.

Demo 4 — Checkpoint Restoration Exercise

  1. Save the current practice file under a separate incident filename so it does not overwrite the controlled checkpoint.
  2. Use File > Open to reopen Chapter10_Risk_Controlled.pkt. This deliberately returns the simulator to a known-good project state.
  3. Verify approved-client connectivity, unused-port shutdowns, and the original sticky MAC binding.
  4. Document which changes made after that checkpoint are absent.

This demonstrates checkpoint selection and verification. It is not a live device configuration restore or a test of recovering production server data. Discuss how real backups would require protected storage, retention, access controls, and separate restoration tests.

9. Instructor Explanation Blocks

Threat, Vulnerability, and Risk

An asset provides value. A threat is a potential cause of harm; a vulnerability is a weakness that can be exploited or triggered. Risk combines the possibility of a harmful event with its consequences. “An unused active jack permits an unapproved device to connect” is more actionable than simply listing “hackers.”

Confidentiality, Integrity, and Availability

Confidentiality concerns unauthorized disclosure, integrity concerns unauthorized or accidental changes, and availability concerns timely access. A preventive control can improve one aspect while harming another: shutdown-mode port security can also interrupt a legitimate device replacement.

Risk Treatment Choices

Mitigate

Reduce likelihood or impact, such as disabling unused ports.

Avoid

Stop an activity creating an unacceptable exposure, such as placing sensitive data in this HTTP demo.

Transfer / Share

Allocate aspects of loss or responsibility through arrangements such as insurance or service contracts; underlying exposure can remain.

Accept

An accountable owner knowingly retains a documented residual risk under defined conditions and review dates.

Preventive, Detective, and Corrective Controls

Unused-port shutdown and MAC limiting are preventive examples. Reviewing violation status is a detective activity. Restoring an approved connection and rolling back a harmful change are corrective actions. Automated monitoring and a full incident-response system are not deployed here.

Recovery Objectives

Recovery time objective (RTO) describes the target time to restore a service; recovery point objective (RPO) describes the acceptable data-loss window. Reopening a saved .pkt file illustrates returning to an earlier state but does not prove that business RTO or RPO requirements have been met.

Discussion Prompts and Expected Answers

  • Is a disabled unused port a fault? No; it is expected behavior under the documented control.
  • Does port security identify a person? No; this example checks source MAC addresses.
  • Does a successful ping prove the portal works? No; application and name-resolution tests are also needed.
  • Did saving a checkpoint eliminate configuration risk? No; checkpoint quality, accessibility, and restoration procedures still matter.
  • Which major risk remains? Shared infrastructure and the combined DNS/HTTP server remain single points of failure.

11. Final Demo Summary

Risk management loop 1. Identify the assets and business dependencies. 2. Describe specific risk scenarios and their consequences. 3. Prioritize using explicit assumptions. 4. Select a treatment and accountable owner. 5. Apply a controlled change and observe its effects. 6. Test expected service and expected restrictions. 7. Practice recovery and retain evidence. 8. Review residual risk and the next action.
Key lesson: A control is useful when it addresses a defined risk, behaves as expected, and has manageable side effects. Verification, recovery practice, and ownership matter as much as the configuration commands.

Final State Checklist

  • Both approved clients reach the server by IP and portal.northstar.com.
  • All documented unused switch ports remain shut down.
  • Staff Fa0/1 is secure-up with the original approved MAC.
  • PC-TEST-01 is disconnected.
  • The baseline and controlled checkpoints remain separate from incident practice files.
  • Residual risks and owners are documented rather than marked automatically resolved.
