1. Lab Purpose

Establish a known-good service baseline, observe network state, and test recovery from selected failures. Students configure a preferred inter-router link and a standby link, verify route changes during an outage, and distinguish link resilience from application recovery.

  • Record reachability, path, interface state, and application behavior before making changes.
  • Explain bandwidth, throughput, latency, jitter, packet loss, and availability.
  • Configure floating static routes in both directions.
  • Demonstrate primary-link failure, backup operation, and return to the preferred path.
  • Show a failure that redundant links cannot fix.
  • Practice a controlled rollback and verify a saved recovery checkpoint.
Instructor note: This is a live teaching demonstration with guided practice, not a graded assignment. The emphasis is evidence-based troubleshooting and recovery verification.
Simulation scope: Packet Tracer demonstrates selected forwarding and failure behavior. Its timing, counters, and traffic generation are not a production throughput benchmark. This exercise protects against loss of one directly connected inter-router link; it does not provide router, switch, server, site, or power redundancy.

2. Lab Scenario

Northstar Training Center uses a shared portal on its services LAN. Two routers connect users to services over separate primary and backup Ethernet links. The administrator must prove that a link outage can be handled and document what remains unavailable during a service failure.

Learning Objectives

  • Define normal operation with repeatable tests rather than a single green link.
  • Explain why a higher administrative distance makes a static route a standby choice.
  • Verify the return path as well as the request path.
  • Compare route availability with application health.
  • Record incident observations, restoration steps, and residual risks.
  • Distinguish redundancy, backup, failover, rollback, RTO, and RPO.

5. Configure Primary and Backup Paths

Part C — Configure the Users Router

Open CLI, answer no to the setup dialog if prompted, and enter:

enable
configure terminal
hostname RTR-USERS-01
interface gigabitEthernet0/0
 description Users LAN gateway
 ip address 192.168.120.1 255.255.255.0
 no shutdown
 exit
interface gigabitEthernet0/1
 description PRIMARY to RTR-SERVICES-01
 ip address 10.12.0.1 255.255.255.252
 no shutdown
 exit
interface gigabitEthernet0/2
 description BACKUP to RTR-SERVICES-01
 ip address 10.12.0.5 255.255.255.252
 no shutdown
 exit
ip route 192.168.121.0 255.255.255.0 10.12.0.2
ip route 192.168.121.0 255.255.255.0 10.12.0.6 10
end
show running-config | include ip route
copy running-config startup-config

Accept the default destination filename by pressing Enter.

Part D — Configure the Services Router

enable
configure terminal
hostname RTR-SERVICES-01
interface gigabitEthernet0/0
 description Services LAN gateway
 ip address 192.168.121.1 255.255.255.0
 no shutdown
 exit
interface gigabitEthernet0/1
 description PRIMARY to RTR-USERS-01
 ip address 10.12.0.2 255.255.255.252
 no shutdown
 exit
interface gigabitEthernet0/2
 description BACKUP to RTR-USERS-01
 ip address 10.12.0.6 255.255.255.252
 no shutdown
 exit
ip route 192.168.120.0 255.255.255.0 10.12.0.1
ip route 192.168.120.0 255.255.255.0 10.12.0.5 10
end

copy running-config startup-config
Route explanation: The final 10 is administrative distance, not hop count, speed, or delay. The primary static route defaults to distance 1. These routes specify the next-hop IP address. The router uses its routing table to determine the outgoing interface for that next hop. The backup stays configured but is normally absent from the active routing table while the preferred route is usable.

Part E — Configure Endpoints and Services

  1. On both PCs and the server open Desktop > IP Configuration > Static and enter the addressing-plan values.
  2. On SRV-PORTAL-01 open Services > DNS, enable DNS, and add portal.northstar.com, type A, address 192.168.121.10.
  3. Open Services > HTTP, enable HTTP, edit index.html, and save:
<html><body>
<h1>Northstar Service Status Portal</h1>
<p>Chapter 12: Performance and Recovery</p>
<p>Portal address: 192.168.121.10</p>
</body></html>

The .com record is resolved inside the simulation; no public DNS or Internet connection is needed. Switches can retain their default access configuration.

6. Record and Verify the Baseline

Part F — Inspect Infrastructure

On both routers:

show ip interface brief
show ip route
show running-config
show interfaces gigabitEthernet0/1
show interfaces gigabitEthernet0/2

All three used interfaces should be up/up. Confirm that both static routes are present in the configuration but the active remote-LAN route uses G0/1 and distance 1. Its route display normally includes [1/0]. The backup interface should be operational even while the route is on standby.

Part G — Verify User Experience

On PC-USER-01:

ipconfig
ping 192.168.120.22
ping 192.168.120.1
ping 192.168.121.10
ping portal.northstar.com
tracert 192.168.121.10

Run a warm-up ping for ARP, then repeat a small fixed set of pings and record actual replies/timeouts. The primary trace normally shows 192.168.120.1, 10.12.0.2, then 192.168.121.10. Formatting and timing may vary.

From both PCs open http://192.168.121.10 and http://portal.northstar.com. Both should show the portal. From the server's Command Prompt, ping both PCs to confirm reverse-direction reachability.

7. Failover and Recovery Demonstrations

Part I — Fail the Primary Physical Link

  1. Confirm both PCs reach the portal and both routers use their primary route.
  2. Record the start of the event. Remove only the cable connecting the two G0/1 interfaces. Leave G0/0 and G0/2 links untouched.
  3. Inspect show ip interface brief on both routers and confirm G0/1 is down.
  4. Run show ip route on both routers. The remote-LAN route should now use G0/2, its backup next hop, and distance 10, normally displayed as [10/0].
  5. Repeat server ping, trace, and a fresh HTTP request from both PCs.

The trace normally changes its second router address to 10.12.0.6. Some packets or sessions may fail during the transition; repeat tests after the routing state settles. Do not promise uninterrupted sessions or a particular recovery time.

Why remove the cable? This intentionally makes the directly connected primary link go down at both endpoints. The configured route depends on that link, so the standby route can take over in each direction.

Part J — Restore the Primary Path

  1. Reconnect RTR-USERS-01 G0/1 to RTR-SERVICES-01 G0/1 with crossover or automatic connection.
  2. Wait for both primary interfaces to return to up/up.
  3. Verify that the preferred distance-1 routes are active again on both routers.
  4. Repeat the user and server tests. Record the observed restoration and any transient failures.

This is failback to the preferred route. The higher-distance route remains configured for future failures. No load balancing or combined capacity is configured.

Part K — Inspect Forwarding in Simulation Mode

  1. In a working copy, select Simulation Mode and filter ARP, ICMP, TCP, DNS, and HTTP.
  2. Generate a fresh server request and step through it using Capture/Forward.
  3. Compare the path before and after a controlled primary-cable removal.
  4. Follow the reply as well as the request to demonstrate the two backup routes.
  5. Restore the cable and return to Realtime.

Cached ARP or DNS entries may hide new lookups. Restart a client in a saved copy if a fresh lookup is necessary; clearing the event list alone does not necessarily clear caches.

Part L — Demonstrate the Limit of Link Redundancy

With both links healthy, turn Services > HTTP Off on the server. Server ping still succeeds and the primary route remains active, but a fresh browser request fails. Restore HTTP On and verify both PCs can load the page.

Failure-detection boundary: These static routes do not monitor portal health or detect every failure beyond an operational next hop. A service outage or a forwarding black hole with the primary interface still up does not automatically select the backup. End-to-end tracking, suitable routing mechanisms, or application health checks would be additional design work.

Part M — Recovery Checkpoint Exercise

  1. Save incident observations in a separate working file, without overwriting the baseline.
  2. Open Chapter12_Recovery_Baseline.pkt.
  3. Repeat route, backup-link, DNS, and HTTP checks; do not assume reopening a file proves it is usable.
  4. Discuss what changes or data created after the checkpoint would be absent.

This restores a simulator project state, not a live production server or device backup. Production recovery testing must cover configuration, application data, storage protection, dependencies, and access to recovery materials.

8. Troubleshooting Demonstrations

One fault at a time: Start with both links healthy and primary routes active. Preserve the baseline, introduce one fault in the working copy, diagnose it, then restore and verify.

Demo 1 — Missing Backup Return Route

On RTR-SERVICES-01 remove its standby route:

enable
configure terminal
no ip route 192.168.120.0 255.255.255.0 10.12.0.5 10
end

Portal access still works over the primary link, hiding the fault. Now remove the primary G0/1-to-G0/1 cable. RTR-USERS-01 installs its backup route, but RTR-SERVICES-01 lacks a route back to the user LAN. Client-to-server tests fail.

Restore the route while the primary cable is still disconnected:

configure terminal
ip route 192.168.120.0 255.255.255.0 10.12.0.5 10
end

Verify backup-path service now works. Reconnect the primary cable and confirm failback. This proves why a standby design must be tested rather than inferred from normal operation.

Demo 2 — Backup Interface Administratively Down

On RTR-USERS-01:

configure terminal
interface gigabitEthernet0/2
 shutdown
end

The primary path still works. Inspect interface state before failing the primary and ask students to predict the outcome. If demonstrating it, remove the primary cable; no usable path remains. Recover the backup:

configure terminal
interface gigabitEthernet0/2
 no shutdown
end

Verify service over the backup, then reconnect the primary and retest. Keeping a route in configuration does not make an unavailable interface usable.

Demo 3 — Name Resolution vs. Connectivity

Change PC-USER-01's DNS to unused 192.168.121.99. Direct-IP HTTP still works. Add a new A record on the server, recoverycheck.northstar.com → 192.168.121.10, and request that name so a cached response cannot hide the error. Restore DNS to 192.168.121.10 and repeat.

Demo 4 — Change Rollback

On RTR-SERVICES-01 temporarily shut down G0/0, the services LAN interface. Both transit links remain operational, but neither path can deliver traffic to the server. Inspect interface state and restore G0/0 with no shutdown. Verify server IP, DNS, and HTTP before marking recovery complete.

9. Instructor Explanation Blocks

Baseline Before Diagnosis

A useful baseline records the normal service, path, and context. Compare the same test from the same endpoint before and after a change. In production, collect time-series measurements over representative workloads rather than extrapolating from a handful of probes.

Monitoring and Capacity Planning

Logs, interface telemetry, flow records, and application checks provide different evidence. Rising utilization, errors, delay, or loss can suggest investigation, but no single counter identifies every cause. SNMP, syslog, flow collection, QoS, and capacity tests are discussion topics here, not configured monitoring systems.

Redundancy vs. Backup

The alternate link provides another live forwarding path. A saved configuration or project provides an earlier state to restore. Neither replaces the other: a second link cannot undo a bad server change, and a saved file does not keep traffic flowing during a cable outage.

Recovery Objectives

RTO is the target time to restore service. RPO describes the acceptable data-loss window. A successful link failover can improve availability without restoring lost application data. Simulator recovery observations do not establish production RTO or RPO compliance.

Backup and Recovery Strategy

Discuss full, incremental, and differential backups, their restore dependencies, protected/off-site copies, and routine restoration tests. Also compare recovery facilities with different readiness levels. This lab contains no production data backup, replication, or disaster recovery site.

Remaining Single Points of Failure

Both paths share the same routers, LAN switches, server, and likely supporting power in the model. A router failure takes down both transit paths. Real resilience requires examining shared physical and operational dependencies, not merely drawing two lines.

Discussion Prompts and Expected Answers

  • Why is the backup route absent from the normal active table? The same destination has a usable lower-distance route.
  • Does distance 10 mean ten hops? No; it is route-source preference.
  • Does successful ping prove HTTP is healthy? No; test the application directly.
  • Will the backup fix a stopped HTTP service? No; the endpoint service is a shared dependency.
  • What proves recovery? Restored intended service and verified configuration, not only an up interface.

11. Final Demo Summary

Normal operation Users LAN -> preferred G0/1 transit -> services LAN Primary static routes: distance 1 Primary cable removed G0/1 goes down on both routers Preferred routes become unavailable Backup static routes through G0/2 become active: distance 10 Verify user requests AND server replies Primary cable restored G0/1 returns up/up Preferred routes become active again Verify DNS, HTTP, path, and both clients
Key lesson: Measure normal behavior, test the failures your design is meant to handle, and verify service after recovery. Redundant links improve only the failure cases they actually cover.

Final State Checklist

  • Both primary and backup cables are connected to the planned ports.
  • All six used router interfaces are up/up.
  • Both primary and backup routes remain in configuration; primary routes are active.
  • Both PCs can reach the server by IP and portal.northstar.com.
  • HTTP is enabled and the page is freshly retrievable.
  • Device startup configurations are saved after repairs; the verified baseline remains separate.
  • Recovery observations and remaining single points of failure are documented.
