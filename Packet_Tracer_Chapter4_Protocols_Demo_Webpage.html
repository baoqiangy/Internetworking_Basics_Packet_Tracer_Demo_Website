1. Lab Purpose

The purpose of this demo lab is to help students understand how network protocols work together to support everyday communication. Students will not only configure devices; they will watch traffic move through the network and identify the protocols involved.

Chapter 3 focused on addressing: MAC addresses, IP addresses, DHCP, DNS, and ports. Chapter 4 expands this by showing how protocols use those addresses to deliver services such as web browsing, name resolution, email, file access, and network testing.

Central teaching idea: A simple user action, such as opening a website, may involve many protocols: ARP, DNS, TCP, HTTP, and sometimes ICMP for troubleshooting.

2. Lab Scenario

You are demonstrating the small-business network for Northstar Training Center. The organization has a local server that provides several common network services. The instructor will use Packet Tracer to show how protocols operate between client devices, a switch, a router, and a server.

Local network
A single LAN subnet connects PCs, a server, a switch, and a router.
Server services
The server provides DNS, HTTP, FTP, and email services for demonstration.
Protocol observation
Simulation Mode is used to observe ARP, DNS, TCP, HTTP, FTP, SMTP, POP3, and ICMP.
Troubleshooting
The instructor intentionally breaks DNS, HTTP, FTP, and email settings to show symptoms and fixes.

3. Learning Objectives

By the end of this demo, students should be able to explain and observe the following:

  1. The role of protocols in network communication.
  2. The difference between protocols at the Data Link, Network, Transport, and Application layers.
  3. How ARP supports local Ethernet delivery.
  4. How DNS resolves a hostname to an IP address.
  5. How TCP supports reliable application communication.
  6. How HTTP uses TCP port 80.
  7. How FTP uses control and data ports.
  8. How SMTP and POP3 support basic email communication.
  9. How ICMP supports connectivity testing with ping.
  10. How Packet Tracer Simulation Mode can be used to inspect protocol behavior.

26. Troubleshooting Demo 1 — DNS Service Off

Break the service

On SRV-HQ-PROTOCOLS-01, go to Services > DNS and turn DNS Off.

Test the symptom

From PC-HQ-CLIENT-01:

ping 192.168.40.10
nslookup www.northstar.com

The ping by IP should work, but name resolution should fail.

Fix the problem

Turn DNS back on, then repeat the nslookup test.

Teaching point: If IP access works but name access fails, suspect DNS.

27. Troubleshooting Demo 2 — HTTP Service Off

Break the service

On the server, go to Services > HTTP and turn HTTP Off.

Test the symptom

nslookup www.northstar.com

Then open:

Ping and DNS may work, but the web page should fail.

Fix the problem

Turn HTTP back on and retry the web browser test.

Teaching point: Network reachability and name resolution can both be correct while an application service is still down.

31. Instructor Explanation — What Happens When a User Opens a Website?

Use this sequence to connect the protocols together:

User enters:
http://www.northstar.com

Step 1: DNS resolves the name.
www.northstar.com -> 192.168.40.10

Step 2: The client checks whether the server is local.
Client: 192.168.40.21/24
Server: 192.168.40.10/24
Both are in 192.168.40.0/24.

Step 3: ARP finds the server MAC address.
Who has 192.168.40.10?

Step 4: TCP connects to the web service.
Destination: 192.168.40.10:80

Step 5: HTTP requests and receives the web page.
Summary line: The user sees one web page, but the network uses several protocols to make that page appear.

32. Instructor Explanation — Ports and Services

A port number identifies a service running on a host. For example:

192.168.40.10:80  = HTTP service
192.168.40.10:53  = DNS service
192.168.40.10:21  = FTP control service
192.168.40.10:25  = SMTP mail sending service
192.168.40.10:110 = POP3 mail retrieval service

The server can use the same IP address for multiple services because each service uses a different port.

33. Instructor Explanation — Protocol Troubleshooting Logic

Use this decision path during the demo:

1. Can the client ping the server IP?
   No  -> Check IP address, subnet mask, cable, switch, server, and router interface.
   Yes -> Continue.

2. Can the client resolve the server name?
   No  -> Check DNS server setting, DNS service status, and DNS records.
   Yes -> Continue.

3. Can the client connect to the service?
   No  -> Check HTTP/FTP/email service status, port, login, and application settings.
   Yes -> Communication is working.

4. Does the problem affect one user or many users?
   One user  -> Check client settings.
   Many users -> Check shared services such as DNS, DHCP, server, or switch.

35. Final Demo Summary

At the end of the demo, emphasize that protocols are not isolated facts. They work together.

When a user opens a webpage by name, the communication may involve:

  1. DNS to resolve the domain name.
  2. ARP to find the local MAC address.
  3. TCP to establish reliable communication.
  4. HTTP to request and receive the webpage.
  5. Ethernet switching to forward frames inside the LAN.
  6. IP addressing to identify the source and destination hosts.
Most important lesson: Network services depend on multiple protocols. Troubleshooting becomes easier when students identify which layer or protocol is failing.
