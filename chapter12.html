Demo 12.1 — Establish a Baseline, Then Troubleshoot Faults

Demo time55–65 minutes
DevicesCumulative multi-VLAN routed topology
Primary focusTroubleshooting method and evidence

Before class

Use a working topology containing DHCP, DNS, VLANs, trunking, inter-VLAN routing, and an ACL. Save a clean baseline copy.

Live demonstration procedure

  1. Before introducing faults, record a baseline: interface status, VLAN table, trunk table, routing table, DHCP leases, successful pings, traceroute path, and website access.
  2. Introduce Fault 1: wrong access VLAN. Start with the user symptom, check link state, IP settings, then switchport VLAN. Correct it and verify all services.
  3. Introduce Fault 2: trunk missing VLAN 20. Show that only one department fails across switches. Use show interfaces trunk and correct allowed VLANs.
  4. Introduce Fault 3: incorrect default gateway from DHCP. Show that local ping works but remote traffic fails. Inspect client settings and DHCP pool.
  5. Introduce Fault 4: DNS record points to the wrong IP. Show that ping by IP works while browsing by name fails or reaches the wrong server.
  6. Introduce Fault 5: ACL rule order blocks legitimate HTTP. Use ACL hit counters and Simulation Mode to find the drop.
  7. For each fault, narrate the seven-step CompTIA process: identify, theory, test, plan, implement/escalate, verify/prevent, document.
  8. End by comparing random command entry with evidence-driven troubleshooting from lower layers upward or by following the likely fault domain.

Command reference

show ip interface brief
show interfaces status
show vlan brief
show interfaces trunk
show ip route
show access-lists
show mac address-table
show arp

What students should observe

Each fault produces a distinct pattern. A baseline shortens diagnosis because the instructor can compare current state with known-good state.

Teaching prompts

Before revealing each fault, ask students for one theory and one command that would test it.

Demo 12.2 — Syslog, SPAN, Backup, and Recovery

Demo time45–55 minutes
Devices1 router, 1 switch, 1 server, 2 PCs
Primary focusMonitoring evidence and configuration recovery

Before class

Use Server0 as a Syslog server if supported. Use a switch model that supports SPAN/port mirroring commands in your Packet Tracer version.

Live demonstration procedure

  1. Enable Syslog service on Server0 and configure the router/switch to send logs to its IP address.
  2. Generate events by shutting and enabling an interface, making a failed login, or causing a port-security violation. Show the received log entries and severity/timestamps where available.
  3. Configure a SPAN session to mirror one source port or VLAN to a monitoring port. Attach a monitoring PC and explain passive observation.
  4. Show the difference between management telemetry (Syslog/SNMP concepts) and packet visibility (SPAN).
  5. Copy the running configuration to startup configuration. Optionally display or copy configuration text to a server using supported TFTP functions.
  6. Deliberately erase or replace a small portion of configuration, such as an interface IP or VLAN assignment, and verify the service outage.
  7. Restore from the saved configuration or reapply the baseline. Measure the logical recovery sequence: identify, restore, validate.
  8. Discuss RPO and RTO using the demo: how much configuration change could be lost, and how quickly must service return?
  9. Finish with a validation checklist covering interface state, addressing, routing, name resolution, policy, and application access.

Command reference

logging 192.168.40.10
logging trap warnings
service timestamps log datetime msec

monitor session 1 source interface f0/1
monitor session 1 destination interface f0/24

copy running-config startup-config
show logging

What students should observe

Logs provide a timeline, SPAN provides packet visibility, and backups reduce recovery time. Recovery is incomplete until end-to-end services are validated.

Teaching prompts

Ask students which events should be logged locally, centrally, or both.

Packet Tracer limitation

SNMP, NetFlow, SPAN, and Syslog command support differs among Packet Tracer devices. Select models and commands that work in the installed version, and present unsupported features conceptually.
