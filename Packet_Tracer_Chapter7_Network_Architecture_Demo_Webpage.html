1. Lab Purpose

Show how the placement of clients, servers, switches, and routers affects the path to an application and the impact of a failure. Students build a small headquarters network and a simulated remote service network, then compare local and remote service access.

  • Identify physical and logical topology, access switching, and routing boundaries.
  • Demonstrate a client/server application across two networks.
  • Compare a local service with a remotely hosted service.
  • Relate the model to hierarchical design, virtualization, and cloud architecture.
  • Use controlled failures to distinguish network availability from application availability.
Instructor note: This is a live demonstration with guided practice, not a graded assignment. The procedures are an original teaching exercise, not a reproduction of the textbook's projects.
Simulation scope: Server-PT devices represent service endpoints. This exercise does not deploy a hypervisor, virtual machines, containers, or an actual public cloud. The remote network is a teaching stand-in for hosted infrastructure; its Ethernet transit link is not a complete ISP or Internet model. No Internet access or cloud account is required.

2. Lab Scenario

Northstar Training Center maintains a local staff portal and is evaluating a remotely hosted learning portal. Two staff computers must reach both services. Students document dependencies and explain which services remain usable when the remote connection fails.

Learning Objectives

  • Label client, service, access, gateway, and transit roles.
  • Explain why an off-subnet destination requires a default gateway.
  • Configure and verify a forward route and a return route.
  • Test local and remote HTTP services by address and DNS name.
  • Trace ARP, ICMP, DNS, TCP, and HTTP in Simulation Mode.
  • Compare peer-to-peer and client/server models, two-tier and three-tier designs, and cloud service models.
  • Explain why two server icons alone do not provide failover.

5. Configure Routers, Servers, and Clients

Part C — Configure the HQ Router

Open the router CLI. If asked to enter the initial configuration dialog, answer no and press Enter.

enable
configure terminal
hostname RTR-HQ-01
interface gigabitEthernet0/0
 description HQ LAN gateway
 ip address 192.168.70.1 255.255.255.0
 no shutdown
 exit
interface gigabitEthernet0/1
 description Transit to RTR-REMOTE-01
 ip address 10.7.0.1 255.255.255.252
 no shutdown
 exit
ip route 192.168.71.0 255.255.255.0 10.7.0.2
end
copy running-config startup-config

Accept the default destination filename by pressing Enter.

Part D — Configure the Remote Router

enable
configure terminal
hostname RTR-REMOTE-01
interface gigabitEthernet0/0
 description Remote service LAN gateway
 ip address 192.168.71.1 255.255.255.0
 no shutdown
 exit
interface gigabitEthernet0/1
 description Transit to RTR-HQ-01
 ip address 10.7.0.2 255.255.255.252
 no shutdown
 exit
ip route 192.168.70.0 255.255.255.0 10.7.0.1
end
copy running-config startup-config

Verify Both Routers

show ip interface brief
show ip route

Both used interfaces should be up/up. HQ should show a static route to 192.168.71.0/24 via 10.7.0.2; the remote router should show a static return route to 192.168.70.0/24 via 10.7.0.1. Connected routes should also appear for each router's LAN and the transit subnet.

Part I — Test the Applications

Part J — Observe Simulation Mode

  1. Switch to Simulation. In Edit Filters, select ARP, DNS, ICMP, TCP, and HTTP.
  2. Generate a new ping or browser request. Use Capture/Forward to advance through events.
  3. Open event envelopes and inspect OSI Model and inbound/outbound PDU details.
  4. Compare a request to the local server with one to the remote server. For a remote destination, the PC sends the Ethernet frame toward its gateway's MAC address.
  5. Notice that routers forward toward the destination IP while Ethernet addressing changes on each routed link. This lab does not translate IP addresses.
  6. Return to Realtime before troubleshooting.
Cache note: Cached ARP or DNS entries can hide lookup steps on repeat requests. Clearing the event list does not necessarily clear caches. To demonstrate fresh lookups, save the baseline, reopen a fresh copy or restart the client, and issue a new request.

7. Network Architecture Demonstrations

Part K — Client/Server and Peer-to-Peer

Have both PCs open the same portal. The PCs request a service and the server supplies it. In a peer-to-peer design, endpoints can both provide and consume resources. A successful PC-to-PC ping shows reachability, not a peer-to-peer application.

Part L — Local vs. Remote Dependencies

Ask students to predict what happens when the transit link fails. On RTR-HQ-01, enter:

enable
configure terminal
interface gigabitEthernet0/1
 shutdown
end

From a PC, ping both server IP addresses and request their pages. The local service should remain reachable, while the remote service fails. Local DNS can still resolve the remote name even though the remote application is unreachable.

Restore the link immediately:

configure terminal
interface gigabitEthernet0/1
 no shutdown
end

Wait for the link to recover and repeat both tests. Do not use a previously displayed browser page as evidence of live connectivity; issue a new request and confirm with ping or Simulation Mode.

Part M — Hierarchical Design and Growth

Access

The HQ switch connects users and local services.

Distribution

In a larger campus, this layer aggregates access networks and applies routing or policy.

Core

A larger design may use a separate high-speed backbone between distribution blocks.

This small topology has access switches and edge routers; it is not a full three-tier campus. Sketch two access switches beneath a combined core/distribution pair to explain a collapsed-core design. Then separate the core and distribution roles to illustrate a three-tier design.

Part O — Resilience and Scale

Identify the HQ switch, each router, the transit link, and the local DNS server as dependencies. Propose redundant equipment, independent links, and replicated services. Explain that additional paths require suitable routing and loop prevention; a second server needs application replication and traffic steering to provide failover. Scaling adds capacity; redundancy addresses failure. Neither is automatically achieved by copying icons.

8. Troubleshooting Demonstrations

One fault at a time: Begin from the working baseline, introduce one change, record the symptom, repair it, and repeat the affected test. Keep the saved baseline intact.

Demo 1 — Wrong Client Gateway

Change PC-HQ-01's gateway to 192.168.70.254. Local server access should work; remote server access should fail. Inspect ipconfig and restore 192.168.70.1. Explain why local delivery does not use the gateway.

Demo 2 — Missing Return Route

On RTR-REMOTE-01 remove the HQ route:

enable
configure terminal
no ip route 192.168.70.0 255.255.255.0 10.7.0.1
end
show ip route

From PC-HQ-01, ping 192.168.71.10. The request can reach the server, but its reply cannot be routed back to the HQ LAN. Follow the return traffic in Simulation Mode. Restore:

configure terminal
ip route 192.168.70.0 255.255.255.0 10.7.0.1
end

Retest from the PC. A router-originated ping may use a different source subnet and can succeed despite the missing HQ route, so the client test matters.

Demo 3 — DNS Failure

Set PC-HQ-01's DNS to 192.168.70.99. Direct-IP page requests should still work. To avoid a cached-name result, add a previously unused A record check.northstar.com → 192.168.71.10 on SRV-HQ-01, then request that name from the PC. It should fail with the wrong DNS setting. Restore DNS to 192.168.70.10 and retry.

Demo 4 — Application Service Stopped

On SRV-REMOTE-01, turn Services > HTTP Off. Ping 192.168.71.10 should still succeed, while a new HTTP request fails. Turn HTTP On and request the page again. Reachability alone does not prove application health.

Demo 5 — Access-Link Failure

Disconnect PC-HQ-02's cable. That PC loses connectivity while PC-HQ-01 can still reach both servers. Reconnect PC-HQ-02 Fa0 to SW-HQ-ACCESS-01 Fa0/2 with a straight-through cable and wait for the link to recover.

Finish with both PCs reaching both server IP addresses and both original DNS names. Save the repaired working copy.

9. Instructor Explanation Blocks

Physical vs. Logical Topology

The cable drawing shows physical connections. The addressing plan and routing table explain logical delivery. Two devices can be physically connected through switches yet require routing if they belong to different IP networks.

Service Placement Changes Dependencies

The local portal needs the local access network. The remote portal additionally depends on gateways, transit connectivity, and the remote network. Centralization can simplify administration while increasing dependence on shared services.

Virtualization Is Not Simulation

A VM runs a guest operating system on virtualized resources. Packet Tracer models selected networking behavior. Its Server-PT icon does not demonstrate CPU allocation, live migration, hypervisor operation, or production application performance.

Security Boundaries Need Policy

Different subnets make routing boundaries visible, but the configured routers permit traffic between these networks. This demo implements no firewall or access-control policy. Discuss where those controls would belong in a larger design.

Discussion Prompts and Expected Answers

  • Does same-LAN traffic need a router? No; it uses local switching when endpoints are in the same subnet.
  • Can DNS succeed while a website fails? Yes; name resolution and application reachability are separate dependencies.
  • Does a remote server automatically constitute cloud computing? No; hosting location alone does not establish a cloud service model.
  • What does a successful ping prove? ICMP reachability at that moment, not HTTP health or available capacity.
  • What would improve remote availability? Independent paths and devices plus service resilience, with appropriate failover mechanisms.

11. Final Demo Summary

End the demonstration by tracing a fresh request:

User opens http://learn.northstar.com 1. The client asks the local DNS server for the destination address. 2. DNS returns 192.168.71.10. 3. The client identifies an off-subnet destination and uses its gateway. 4. HQ routes toward 10.7.0.2 across the transit network. 5. The remote router forwards traffic onto the remote service LAN. 6. TCP and HTTP carry the request and response. 7. The return route carries the response back to the HQ client.
Key lesson: Network architecture determines where services live, how users reach them, and which failures affect them. A working application depends on both the network path and the services at its endpoints.
