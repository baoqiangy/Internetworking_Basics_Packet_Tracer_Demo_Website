1. Lab Purpose

Connect a branch office to headquarters through a simulated provider network. Students configure point-to-point links and routing, access a central application, and distinguish a working local network from a working WAN path.

  • Identify customer edge, provider, and local access roles.
  • Address two point-to-point WAN links using /30 subnets.
  • Configure serial PPP links and identify DCE clocking.
  • Use default routes at the customer sites and specific return routes in the provider network.
  • Verify DNS and HTTP access across multiple routers.
  • Compare legacy serial links with modern WAN options and discuss VPN and SD-WAN roles.
  • Introduce and repair link, encapsulation, routing, and DNS faults.
Instructor note: This is a live teaching demo with guided practice, not a graded assignment. Prepare a working baseline before class.
Model scope: Serial PPP is used to make point-to-point link behavior visible. It is a teaching model, not a recommendation for a new production WAN. The provider router represents a simplified routed private service, not the public Internet, MPLS internals, or an actual carrier network. The baseline includes no NAT, VPN encryption, authentication, or redundant path.

2. Lab Scenario

Northstar Training Center has a headquarters server and a small branch classroom. The branch must access the central portal through a provider connection. Staff need to isolate faults by determining whether the local LAN, WAN link, route, DNS service, or application has failed.

Learning Objectives

  • Explain the difference between LAN connectivity and end-to-end WAN connectivity.
  • Identify the two usable addresses in each /30 link network.
  • Distinguish DCE clocking, PPP encapsulation, and IP routing.
  • Configure default routes and return routes without a dynamic routing protocol.
  • Trace a request from a branch PC to the headquarters server.
  • Explain why PPP encapsulation alone does not encrypt traffic.
  • Discuss availability, latency, throughput, and provider service commitments without treating simulation timing as a benchmark.

4. Build the Packet Tracer Network

Part A — Create the Project and Install Modules

  1. Create a new file and save it as Chapter9_Wide_Area_Networking_Demo.pkt.
  2. Add and rename the three 1941 routers, two switches, three PCs, and one server.
  3. For each router, open the Physical tab and switch off its power.
  4. Insert one HWIC-2T into the first compatible module slot, then switch the router on.
  5. Check show ip interface brief. The commands below assume S0/1/0 and S0/1/1. If the slot yields different numbering, substitute the actual names throughout.
  6. Label the two LANs and WAN subnets in the workspace. Put the provider in the center.

Part C — Cable the WAN Links

  1. Select the Serial DCE cable. Click RTR-PROVIDER-01 first and choose S0/1/0; connect the other end to RTR-HQ-01 S0/1/0.
  2. Select another Serial DCE cable. Click RTR-PROVIDER-01 first and choose S0/1/1; connect the other end to RTR-BRANCH-01 S0/1/0.
  3. Verify the DCE side using show controllers serial 0/1/0 and show controllers serial 0/1/1 on the provider. Look for DCE in the output.
Clocking: The configuration assumes the provider is DCE on both links. If inspection shows otherwise, reconnect the cable to match the plan or apply clock rate only to the actual DCE endpoint. DCE/DTE describes this serial-link role; it is not the same as an IP address or routing role.

Part D — Configure Headquarters

Open CLI, answer no to the initial configuration dialog if prompted, and press Enter.

configure terminal
hostname RTR-HQ-01

Routing explanation: Each edge sends unknown destinations toward the provider. The provider must know the customer LAN routes to forward traffic to those sites. A default route does not provide Internet access by itself. There is no upstream Internet network in this topology.

Part G — Configure PCs and Server

On every endpoint, open Desktop > IP Configuration, select Static, and enter its address, mask, gateway, and DNS from the plan.

On SRV-HQ-01, open Services > DNS, turn DNS On, and add:

Open Services > HTTP, enable HTTP, edit index.html, and save:

<html><body>

<p>Central service: 192.168.90.10</p>

The .com name is resolved by the simulation's local DNS server. No public DNS change or domain registration is required. Switches can remain in their default access VLAN.

6. Verify Site-to-Site Connectivity

Part H — Verify Link and Routing State

On all three routers:

show ip interface brief
show ip route
show interfaces serial0/1/0

On the provider, also run show interfaces serial0/1/1. Both WAN links should be up/up and show PPP encapsulation. HQ and branch should each have an S* default route. The provider should have two connected WAN networks and static routes to both LANs.

Part I — Test from the Branch

On PC-BRANCH-01, open Desktop > Command Prompt:

ipconfig
ping 192.168.91.22
ping 192.168.91.1
ping 10.9.0.5
ping 192.168.90.1
ping 192.168.90.10
ping portal.northstar.com
tracert 192.168.90.10

All pings should succeed. The trace normally shows branch gateway 192.168.91.1, provider 10.9.0.5, HQ WAN interface 10.9.0.1, and the server. Display details can vary with Packet Tracer version. Repeat an initial ping if ARP resolution consumes the first attempt.

From PC-HQ-01, ping both branch PCs to verify reverse-direction reachability. On both branch PCs, open Desktop > Web Browser and request:

http://192.168.90.10
http://portal.northstar.com

Confirm that both requests display the HQ portal. Test the same page from the HQ PC.

Checkpoint: Save a verified copy as Chapter9_WAN_Baseline.pkt. Use a separate working copy for demonstrations and faults.

Part J — Trace the Request in Simulation Mode

  1. Switch to Simulation and select ARP, DNS, ICMP, TCP, and HTTP in Edit Filters.
  2. Issue a fresh branch ping or portal request and advance with Capture/Forward.
  3. Observe Ethernet/ARP on the LANs and forwarding through the serial links. Point-to-point PPP does not use Ethernet ARP to discover its peer.
  4. Inspect IP source/destination addresses and each router's forwarding decision. This lab does not translate addresses.
  5. Follow replies as well as requests to emphasize return routes.
  6. Return to Realtime before introducing faults.

Cached ARP or DNS entries may suppress fresh lookup events. Restart a client in the saved working copy when a fresh lookup is needed; clearing the event list alone does not necessarily clear caches.

7. WAN Demonstrations

Part K — WAN Failure vs. Local Availability

Before making a change, ask which services will still work. On RTR-BRANCH-01:

enable
configure terminal
interface serial0/1/0
 shutdown
end

From PC-BRANCH-01, ping its local peer .22 and gateway 192.168.91.1; both should still work. Ping 192.168.90.10 and issue a fresh portal request; both should fail. The HQ PC should still reach the HQ server. Branch name lookups also depend on the HQ DNS service, although a cached result may still appear.

Restore the WAN link:

configure terminal
interface serial0/1/0
 no shutdown
end

Wait for PPP to recover and repeat all tests. A page already visible in a browser is not proof that the WAN is working; request it again and corroborate with ping or simulation events.

Part L — Clock Rate vs. Bandwidth

On the provider, inspect a serial interface's configuration and status. The clock rate 64000 command supplies timing on this lab's DCE endpoint. The bandwidth interface command is an informational value used by features such as routing metrics; changing it is not a physical speed control. Do not use simulator ping times to claim production WAN throughput or latency.

Part M — Compare WAN Transport Choices

OptionTeaching PointRelationship to This Lab
Private point-to-point serviceConnects sites through a contracted path or serviceSerial links illustrate link and routing dependencies
Carrier EthernetProvides an Ethernet service handoff; service scope and responsibilities depend on the contractDiscuss replacing serial handoffs with provider Ethernet
Provider MPLS serviceUses provider forwarding mechanisms to deliver services between customer sites; privacy does not itself imply encryptionThe simple provider router does not simulate MPLS labels or VPN internals
Business Internet over fiber, cable, or DSLProvides an underlay over which applications or encrypted tunnels can runNo public Internet is built here
Cellular or satelliteCan provide access or an alternate path; coverage, capacity, latency, and cost varyDiscuss as alternate transports, not configured links

Part N — VPN, SD-WAN, and Resilience

VPN

An appropriately configured encrypted VPN can protect traffic over an underlying network. PPP framing alone does not encrypt this demo's traffic.

SD-WAN

Uses policy and orchestration to manage WAN paths and application traffic. Multiple links alone do not constitute an SD-WAN deployment.

Resilience

Independent links and providers can reduce shared failure risks, but routing, failure detection, and application behavior determine failover.

Ask students to sketch a second branch path and name the additional routing decisions it would require. Discuss demarcation, customer equipment, provider responsibilities, availability targets, and escalation contacts. These are design discussions; automatic failover is not configured in this baseline.

8. Troubleshooting Demonstrations

One fault at a time: Begin from the working baseline. Record the symptom, inspect the likely layer, repair the fault, and repeat the affected tests before proceeding.

Demo 1 — Encapsulation Mismatch

On RTR-BRANCH-01, change only its serial interface to HDLC:

enable
configure terminal
interface serial0/1/0
 encapsulation hdlc
end
show interfaces serial0/1/0

The branch and provider encapsulations no longer match. After the protocol settles, the line protocol should fail; exact status timing can vary. Local branch communication remains available but HQ access fails. Inspect both ends, then restore:

configure terminal
interface serial0/1/0
 encapsulation ppp
end

Demo 2 — Missing Provider Return Route

On RTR-PROVIDER-01:

enable
configure terminal
no ip route 192.168.91.0 255.255.255.0 10.9.0.6
end
show ip route

From PC-BRANCH-01 ping 192.168.90.10. The request can reach HQ, but the provider cannot route the reply back to the branch LAN. A ping sourced by the branch router from its serial address can still succeed because that transit network remains connected at the provider. Test from the endpoint, not only the router.

Restore on the provider:

configure terminal
ip route 192.168.91.0 255.255.255.0 10.9.0.6
end

Demo 3 — Missing Branch Default Route

On RTR-BRANCH-01:

configure terminal
no ip route 0.0.0.0 0.0.0.0 10.9.0.5
end
show ip route

The local LAN and directly connected provider interface remain reachable, but the HQ LAN is unknown. Restore:

configure terminal
ip route 0.0.0.0 0.0.0.0 10.9.0.5
end

Demo 4 — Wrong Client DNS

Change PC-BRANCH-01's DNS setting to unused 192.168.91.99. Server-IP ping and direct-IP HTTP should still work. On the HQ server add a previously unused A record wancheck.northstar.com pointing to 192.168.90.10, then request that new name from the branch PC so a cached answer does not hide the failure. Restore DNS to 192.168.90.10 and repeat the name request.

Demo 5 — Wrong Endpoint Gateway

Change PC-BRANCH-02's gateway to unused 192.168.91.254. Its same-LAN peer stays reachable, but HQ access fails. PC-BRANCH-01 should continue working. Restore the gateway to 192.168.91.1.

9. Instructor Explanation Blocks

Link State Is Not End-to-End Reachability

A WAN interface can be up/up while user traffic fails because of missing routes, bad endpoint gateways, or a stopped service. Work outward from the endpoint and verify the return path.

Default Routes and Specific Routes

An edge default is useful when one provider is the exit for unknown destinations. The provider's specific LAN routes identify which edge serves each site. Routing uses the most specific matching route.

Encapsulation Is Not Encryption

PPP provides framing and link negotiation. Optional PPP authentication is distinct from traffic encryption; neither authentication nor encryption is configured here. A private WAN service also should not be assumed to encrypt payloads automatically.

Demarcation and Operational Ownership

The service handoff marks an agreed responsibility boundary. In practice, ownership and troubleshooting responsibilities depend on the service contract and equipment arrangement. The lab's provider router makes that conceptual boundary visible.

Performance and Service Commitments

Bandwidth, achieved throughput, latency, jitter, packet loss, and availability describe different properties. Service-level agreements define measurable commitments and remedies. This simulator demonstrates packet paths and selected failure behavior, not a production capacity test.

Discussion Prompts and Expected Answers

  • Why can branch PCs still communicate during a WAN outage? Their local traffic remains on the branch LAN.
  • Why might a router ping succeed when a PC ping fails? The probes can use different source subnets with different return-route requirements.
  • Does a default route create an Internet connection? No; it only specifies where unmatched traffic is forwarded.
  • Does PPP secure portal contents? No; PPP framing alone does not encrypt them.
  • Is changing interface bandwidth the same as changing clock rate? No; they serve different purposes.

11. Final Demo Summary

Trace a fresh branch request to the central service:

PC-BRANCH-01 opens http://portal.northstar.com 1. The PC sends its DNS query toward local gateway 192.168.91.1. 2. The branch default route forwards it to provider 10.9.0.5. 3. The provider route sends HQ-bound traffic to 10.9.0.1. 4. HQ delivers the query to DNS server 192.168.90.10. 5. DNS replies use the HQ default and provider branch-LAN route. 6. The client sends TCP/HTTP traffic to the resolved server address. 7. Requests and replies traverse both PPP links and the site LANs.
Key lesson: A working WAN application depends on local access, operational links, correct forwarding and return routes, and healthy services. A green link or a successful router ping proves only part of that path.
