01Objectives & precautions

DHCP snooping is a Layer 2 security feature that checks DHCP packets arriving on switch ports. An administrator marks the port toward an authorized DHCP server as trusted; ordinary client and unknown-server ports remain untrusted. Server-originated DHCP responses arriving on untrusted ports are discarded.

  • Demonstrate a rogue DHCP server distributing incorrect settings.
  • Enable DHCP snooping for VLAN 10 and trust only the authorized server port.
  • Show that the client receives a valid lease after protection is enabled.
  • Inspect snooping configuration and the learned DHCP binding table.
Safety: Use only an isolated Packet Tracer network. Do not connect the rogue DHCP server to a real production network. Packet Tracer models and versions vary; some CLI commands, packet filters, and binding outputs may not be fully implemented.

03Build the Packet Tracer network

  1. Open Packet Tracer and drag a Cisco 2960 switch onto the workspace.
  2. Add two servers (Server0, Server1) and one PC (PC0).
  3. Use Copper Straight-Through cables to connect Server0 → Fa0/1, PC0 → Fa0/2, and Server1 → Fa0/3.
  4. Wait for interfaces to turn green. Rename devices for clarity.

04Configure legitimate DHCP server

  1. Server0 → Desktop → IP Configuration: set static IP 192.168.10.2, mask 255.255.255.0.
  2. Server0 → Services → DHCP.
  3. Turn the DHCP service On, create/edit a pool named AUTHORIZED, fill the fields below, and click Add or Save as your version requires.
FieldValue

Expected authorized leases: approximately 192.168.10.100–192.168.10.149. Actual first allocation depends on available addresses.

05Configure rogue DHCP server

  1. Server1 → Desktop → IP Configuration: static IP 192.168.10.3, mask 255.255.255.0.
  2. Server1 → Services → DHCP, turn service On and configure a second pool:

Why this matters: A client accepting this rogue offer may use an incorrect gateway or DNS server. The rogue server in this demo is only a deliberately misconfigured training device.

All three ports must be in the same VLAN so broadcast DHCP messages reach both servers during the baseline test.

07Baseline: test without snooping

  1. On PC0 select Desktop → IP Configuration → DHCP.
  2. Observe the assigned IPv4 address, default gateway, and DNS setting.
  3. Switch to Simulation Mode; filter for DHCP (and optionally ARP). Repeat the DHCP request by toggling Static → DHCP, or using the PC Command Prompt commands supported by your Packet Tracer version.
  4. Watch DHCP Offers from both servers in the event list. Depending on timing, the PC may accept either one.
PC0 Command Prompt (if supported)
ipconfig /all
ipconfig /release
ipconfig /renew
Expected baseline: The client may receive either the legitimate 192.168.10.100+ address or rogue 192.168.10.200+ address. Do not claim the rogue server always wins; DHCP offer timing is nondeterministic.

If the device rejects ip dhcp snooping, try a supported Cisco switch model in Packet Tracer. Some models expose a subset of IOS features; see the fallback section. Do not interpret a command accepted by the CLI as proof that the simulation accurately filters packets.

09Enable DHCP snooping

Cisco IOS / Command
enable
configure terminal
ip dhcp snooping
ip dhcp snooping vlan 10
! Optional for compatibility with Packet Tracer server behavior:
no ip dhcp snooping information option
interface fastEthernet0/1
 ip dhcp snooping trust
exit
interface fastEthernet0/2
 no ip dhcp snooping trust
 ip dhcp snooping limit rate 10
exit
interface fastEthernet0/3
 no ip dhcp snooping trust
exit
end
show ip dhcp snooping
Instructor note: Trust only Fa0/1. The client Fa0/2 and rogue server Fa0/3 remain untrusted. The rate limit is optional and should be applied conservatively; omit an unsupported line rather than assuming it worked. Option 82 is disabled in this classroom example for compatibility; real deployments should follow their network design.

10Demonstrate blocked rogue offers

Packet flow after enabling DHCP snooping; rogue server responses on untrusted Fa0/3 are discarded.
  1. On PC0 reopen Desktop → IP Configuration.
  2. Change to Static, then back to DHCP (or release/renew the lease).
  3. Observe the assigned address; expected: 192.168.10.100–149, from Server0.
  4. Use Simulation Mode with DHCP filtered, if the version supports showing rejected messages.
  5. Compare results before and after enabling snooping.
A successful demonstration requires confirmation that the legitimate lease succeeds while server-originated messages from Fa0/3 are blocked. If the GUI does not show the drop, verify settings and results using CLI and repeated renewals. Simulation visualizations vary by version.

11Verify bindings and port trust

Cisco IOS / Command
show ip dhcp snooping
show ip dhcp snooping binding
show running-config

Look for DHCP snooping enabled on VLAN 10, Fa0/1 listed as trusted, and other ports untrusted. A learned binding might resemble the following (illustrative only):

Illustrative output
MacAddress         IpAddress        Lease(sec)  Type      VLAN  Interface
00:11:22:33:44:55  192.168.10.100   86400       dhcp-snooping 10    Fa0/2

Explanation: The binding associates the client MAC address, leased IP address, VLAN, and switch interface. It supports other protections, such as Dynamic ARP Inspection. Not every Packet Tracer switch populates every field exactly like physical equipment.

12DHCP message flow explained

DORA: Discover, Offer, Request, Acknowledgment
MessageOriginSnooping action
DHCPDISCOVERClientNormally allowed from untrusted client port
DHCPOFFERServerAllowed from trusted server-facing port; blocked from untrusted rogue-facing port
DHCPREQUESTClientAllowed subject to snooping checks
DHCPACKServerAccepted from trusted port; supports learning lease binding

13Troubleshooting and fallback

SymptomCheck / fix
ip dhcp snooping rejectedTry another supported 2960 model / Packet Tracer release; document lack of support.
Client gets no lease after snoopingEnsure Fa0/1 (legitimate server link) is trusted, VLAN 10 is enabled, links active, server DHCP On.
Client still gets rogue addressConfirm rogue is on Fa0/3 untrusted; renew lease rather than relying on previously obtained address.
Binding table emptyRenew lease after snooping is enabled; verify client port and supported simulation behavior.
Option 82 prevents server operationTry no ip dhcp snooping information option if supported, or a compatible server configuration.
Rate-limit command rejectedLeave rate limiting out; it is optional for the core demo.
No visible packet drop in Simulation ModeUse CLI verification and lease outcomes; Packet Tracer might not animate drop events.
Fallback if unsupported: Keep both DHCP servers active and demonstrate the baseline race using DHCP packets in Simulation Mode. Then explain the trusted-port filter using the included packet-flow diagram and Cisco command reference. Be clear that this is a conceptual demonstration, not verified DHCP snooping enforcement.

14Cleanup & reset

Remove DHCP snooping and optional rate limiting at the end of the demo:

Cisco IOS / Command
enable
configure terminal
no ip dhcp snooping vlan 10
no ip dhcp snooping
interface fastEthernet0/1
 no ip dhcp snooping trust
exit
interface fastEthernet0/2
 no ip dhcp snooping limit rate
exit
end
show ip dhcp snooping

Turn Server1 → Services → DHCP → Off to remove the rogue server from the scenario. Optionally save a copy of the Packet Tracer project before cleanup to reuse in class.

Key takeaway: DHCP snooping prevents unauthorized DHCP server replies on untrusted switch ports while allowing approved server replies through trusted interfaces. Trust placement and per-VLAN enablement matter more than simply entering the global command.
