1. Lab Purpose

Turn a written access policy into testable network behavior. Students enable authenticated SSH management, restrict management access to one administrative workstation, and permit guest access only to selected shared services.

  • Distinguish identification, authentication, authorization, and accounting.
  • Define permitted sources, destinations, and services before entering commands.
  • Configure SSH version 2 with a local administrative account.
  • Use a standard ACL to restrict remote management by source address.
  • Use an extended ACL to allow guest DNS and HTTP while denying other routed guest traffic.
  • Verify both permitted and denied cases, then diagnose rule order and placement errors.
Instructor note: This original lab is an instructor demonstration with guided practice, not a graded assignment. Keep direct router CLI access available for recovery while testing remote-management restrictions.
Scope: The lab uses static addresses, local router authentication, and stateless IPv4 ACLs. It does not configure centralized AAA, MFA, 802.1X, a stateful firewall, application user roles, or full accounting. Source IP addresses are policy selectors, not proof of a person's identity.

2. Lab Scenario

Northstar Training Center has staff, guest, and services networks. Guests may use the shared portal and its DNS server but must not reach staff computers or manage the router. Only the designated admin workstation may establish a router SSH session.

Learning Objectives

  • Translate a policy table into source/destination/protocol decisions.
  • Demonstrate a correct password from an allowed source and a rejected password.
  • Show that valid credentials alone do not bypass a source restriction.
  • Explain first-match processing and the implicit deny.
  • Distinguish access-class on VTY lines from ip access-group on interfaces.
  • Explain why a blocked ping can coexist with a working website.
  • Recognize the limits of network ACLs and local privilege levels.

5. Configure the Network and SSH Management

Part C — Configure Router Interfaces

Open RTR-HQ-01 CLI. Answer no to the initial setup dialog if prompted.

enable
configure terminal
hostname RTR-HQ-01
interface gigabitEthernet0/0
 description Staff and admin LAN
 ip address 192.168.110.1 255.255.255.0
 no shutdown
 exit
interface gigabitEthernet0/1
 description Guest LAN - policy applied inbound later
 ip address 192.168.111.1 255.255.255.0
 no shutdown
 exit
interface gigabitEthernet0/2
 description Shared services LAN
 ip address 192.168.112.1 255.255.255.0
 no shutdown
 exit
end

Part D — Configure Endpoints and Shared Services

  1. On each endpoint, choose Desktop > IP Configuration > Static and enter the plan's address, mask, gateway, and DNS.
  2. On SRV-HQ-01, open Services > DNS, turn DNS On, and add the A record portal.northstar.com → 192.168.112.10.
  3. Open Services > HTTP, turn HTTP On, edit index.html, and save:
<html><body>
<h1>Northstar Shared Portal</h1>
<p>Chapter 11: Access Control Demo</p>
<p>Guests may use this web service and its DNS server.</p>
</body></html>

The .com DNS name is local to the simulation. The page contains fictional, non-sensitive content; HTTP is unencrypted. A network ACL permitting HTTP does not authenticate website users.

Part E — Enable Local SSH Authentication

On the router, enter:

configure terminal
ip domain-name northstar.com
username netadmin privilege 15 secret N0rthstar-Admin11!
crypto key generate rsa

At the modulus prompt, enter 2048. Wait for key generation, then continue:

ip ssh version 2
line vty 0 4
 login local
 transport input ssh
 exec-timeout 5 0
 exit
end
show ip ssh
show line

If additional VTY lines 5–15 exist on the selected image, disable their remote transport so they cannot provide an alternate path:

configure terminal
line vty 5 15
 transport input none
end

If that line range does not exist, omit that block; inspect show line and show running-config rather than assuming every image has the same VTY count. Verify SSH version 2 before proceeding. If the simulator image rejects 2048-bit keys, use a compatible router/image for this demo.

Classroom credential: netadmin / N0rthstar-Admin11! is a published simulation-only account with full privilege 15. It is not a production password or a demonstration of granular role-based authorization. The domain-name command supports the router's SSH identity setup; it does not create a DNS record.

6. Verify the Working Baseline

Part F — Check Networking Before Filtering

On the router:

show ip interface brief
show ip route
show ip ssh

Expect all three interfaces up/up and connected routes for all three LANs. On the admin PC, ping the staff PC and server. On the guest PC, ping its gateway, staff PC 192.168.110.22, and server 192.168.112.10. All should work at this stage.

From every PC, browse to http://192.168.112.10 and http://portal.northstar.com. Repeat an initial ping if ARP causes a first-packet timeout.

Part G — Verify Authentication and Transport

From PC-ADMIN-01 Command Prompt:

ssh -l netadmin 192.168.110.1

Enter the classroom password. Expect the privileged RTR-HQ-01# prompt. Run show ip interface brief, then exit. Repeat with an incorrect password and confirm authentication fails.

Before applying the source ACL, test the same correct login from PC-STAFF-01. It should succeed; this establishes that SSH reachability exists before source restriction. Exit the session.

From the admin PC, attempt telnet 192.168.110.1. It should fail because the enabled VTY lines accept SSH only.

Checkpoint: On the router run copy running-config startup-config, accept the filename, and save Chapter11_Access_Baseline.pkt. Use Save As to create a separate working copy for ACL changes.

7. Apply and Test Access Controls

Part H — Restrict Router Management to the Admin PC

Using direct router CLI, define a standard ACL and apply it to the enabled VTY lines:

configure terminal
ip access-list standard ADMIN-SOURCES
 permit host 192.168.110.21
 deny any
 exit
line vty 0 4
 access-class ADMIN-SOURCES in
 exit
end

Open a new admin SSH session; it should succeed with valid credentials. Exit, then open a new session from PC-STAFF-01 using the same account; it should be blocked. Test new sessions because a previously established session may not be a reliable test of admission controls.

Inspect show access-lists and the VTY portion of show running-config. The explicit deny makes the policy visible; an implicit deny exists even without that line. The restriction governs remote terminal access, not ordinary routed portal traffic.

Part I — Permit Guest DNS and HTTP Only

Create the extended ACL in its complete intended order, then attach it inbound on the guest-facing interface:

configure terminal
ip access-list extended GUEST-IN
 permit udp 192.168.111.0 0.0.0.255 host 192.168.112.10 eq 53
 permit tcp 192.168.111.0 0.0.0.255 host 192.168.112.10 eq 53
 permit tcp 192.168.111.0 0.0.0.255 host 192.168.112.10 eq 80
 deny ip any any
 exit
interface gigabitEthernet0/1
 ip access-group GUEST-IN in
 exit
end
show access-lists
show ip interface gigabitEthernet0/1

The source wildcard 0.0.0.255 matches the /24 guest range. host selects one destination. Each eq after the destination matches its service port. Both DNS transports are permitted even if the simulator's simple query uses UDP.

“Inbound” means packets entering the router from the guest LAN. Server replies leave toward the guest through this interface, so this inbound ACL does not inspect those reply packets. This is directional filtering, not stateful connection tracking.

Part K — Observe Rule Matching

  1. Use Simulation Mode with DNS, TCP, HTTP, and ICMP filters.
  2. From the guest, request the portal and observe forwarding toward the server.
  3. Send a guest ping to the server and inspect where the router drops it.
  4. Return to Realtime and inspect show access-lists; compare rule counters before and after tests where supported.
  5. Record both successful and denied results rather than only checking connectivity.

Cached DNS can hide a query. Add a fresh server A record accesscheck.northstar.com → 192.168.112.10 and request that name when you need evidence of a new lookup.

Policy limits: The ACL is stateless. Replies sent from a guest to a staff-initiated connection can also be denied; do not claim unrestricted staff-to-guest sessions. Same-LAN guest traffic does not pass through this router ACL. Source-IP restrictions also do not authenticate a user or replace endpoint, physical, or application controls.

When the matrix passes, save router startup configuration and save Chapter11_Access_Controlled.pkt. Preserve this file before troubleshooting.

8. Troubleshooting and Recovery

One change at a time: Work in a separate copy, keep direct router CLI available, and retest the whole acceptance matrix after recovery. Do not save intentional faults over the controlled checkpoint.

Demo 1 — Incorrect Admin Source

Use direct router CLI to replace the permitted admin address with unused .99:

configure terminal
no ip access-list standard ADMIN-SOURCES
ip access-list standard ADMIN-SOURCES
 permit host 192.168.110.99
 deny any
 exit
end

Only test after the complete replacement exists. A new admin SSH session should fail even with valid credentials. Restore from direct CLI:

configure terminal
no ip access-list standard ADMIN-SOURCES
ip access-list standard ADMIN-SOURCES
 permit host 192.168.110.21
 deny any
 exit
end

The VTY attachment remains configured. Verify a new admin session succeeds and a staff session fails. Deleting an applied ACL can create a transient policy gap, so this classroom replacement technique belongs in the isolated working copy; production changes require an appropriate change procedure.

Demo 2 — Missing DNS Permission

On the router remove only the DNS permits:

configure terminal
ip access-list extended GUEST-IN
 no permit udp 192.168.111.0 0.0.0.255 host 192.168.112.10 eq 53
 no permit tcp 192.168.111.0 0.0.0.255 host 192.168.112.10 eq 53
 exit
end

Guest direct-IP HTTP should still succeed. Add a new DNS name dnscheck.northstar.com → 192.168.112.10 on the server and request it from the guest; a fresh lookup should fail. A cached portal name is not a reliable DNS test.

Demo 3 — Rule Order Mistake

While the DNS fault is present, append the same two permits with unnumbered commands:

configure terminal
ip access-list extended GUEST-IN
 permit udp 192.168.111.0 0.0.0.255 host 192.168.112.10 eq 53
 permit tcp 192.168.111.0 0.0.0.255 host 192.168.112.10 eq 53
 exit
end
show access-lists

Inspect the displayed order. On the target IOS behavior, the newly appended entries appear after the existing deny ip any any, so DNS is still denied. First match wins; the router does not search for a later, more permissive rule. If a simulator version handles insertion differently, use the actual displayed order to explain the result.

Repair the Guest Policy in Its Intended Order

For this isolated classroom copy, briefly detach and rebuild the ACL. Guest traffic is unrestricted during detachment, so finish the procedure before resuming tests.

configure terminal
interface gigabitEthernet0/1
 no ip access-group GUEST-IN in
 exit
no ip access-list extended GUEST-IN
ip access-list extended GUEST-IN
 permit udp 192.168.111.0 0.0.0.255 host 192.168.112.10 eq 53
 permit tcp 192.168.111.0 0.0.0.255 host 192.168.112.10 eq 53
 permit tcp 192.168.111.0 0.0.0.255 host 192.168.112.10 eq 80
 deny ip any any
 exit
interface gigabitEthernet0/1
 ip access-group GUEST-IN in
 exit
end

Verify ordered rules, attachment direction, a fresh DNS lookup, guest HTTP success, and guest ICMP denial.

Demo 4 — Wrong Local Password

From the allowed admin PC, attempt SSH with an incorrect password. Network access reaches the authentication stage but login fails. Use the correct classroom password and verify success. Compare this with a non-admin source being blocked before it can establish a normal login session.

9. Instructor Explanation Blocks

Identification, Authentication, Authorization, Accounting

The username identifies an account. The password authenticates the account in this local example. The account's privilege and policy decisions control permitted actions. Accounting records activity; a complete accounting system is not configured here. ACL counters provide limited packet-match evidence, not a user audit trail.

Least Privilege and Default Deny

The guest policy names exactly the shared services it needs. Unlisted routed guest traffic is denied. The admin account has full device privilege for teaching convenience, so it is not an example of granular administrator least privilege.

Standard vs. Extended ACL

The standard ACL selects management sources. The extended ACL selects source, destination, IP protocol, and service port. Both are ordered lists. An ACL definition does nothing until used by an appropriate feature or interface.

Management Access vs. Transit Traffic

access-class on VTY lines controls remote terminal access to the router. ip access-group filters IP packets at an interface. Keeping these purposes distinct helps avoid blocking unrelated user services while fixing management policy.

Identity-Based Controls Beyond This Demo

Centralized RADIUS or TACACS+ can support device or network access workflows. MFA adds another authentication factor; 802.1X controls port-based network admission with an authenticator and authentication service. Application roles determine what signed-in users can do inside a service. These mechanisms solve different problems and are discussed rather than configured here.

Access-Control Models

Role-based access ties permissions to job functions; attribute-based decisions evaluate attributes and context; discretionary models allow resource owners to grant access; mandatory models enforce centrally defined classifications or labels. A source-IP ACL does not implement all of these models or establish a zero-trust architecture by itself.

Discussion Prompts and Expected Answers

  • Can valid credentials still be denied? Yes; network source policy can prevent access to the login service.
  • Does allowing TCP 80 prove a visitor is authorized to see every web page? No; the application needs its own authorization.
  • Why permit both UDP and TCP 53? DNS can use either transport, even if this demo's simple lookup uses UDP.
  • Why does guest gateway ping fail? The ingress IPv4 ACL also filters that ICMP packet.
  • Why test denied traffic? Successful permitted traffic alone does not prove the restriction works.

11. Final Demo Summary

Guest opens http://portal.northstar.com 1. Guest sends a DNS query toward its gateway. 2. GUEST-IN permits DNS only to 192.168.112.10. 3. DNS returns the shared server's address. 4. GUEST-IN permits the guest's TCP 80 request to that server. 5. Server replies leave toward the guest; no outbound ACL is applied. 6. Other guest IPv4 traffic is denied on ingress. Admin opens SSH to 192.168.110.1 1. VTY source ACL admits 192.168.110.21. 2. SSH protects the remote management session. 3. Local login checks netadmin's password. 4. The classroom account receives configured privilege 15.
Key lesson: Define who or what may reach each service, apply the appropriate control, and verify both permissions and denials. Authentication, network filtering, and application authorization are complementary.

Final State Checklist

  • Admin SSH succeeds with the correct password and fails with an incorrect one.
  • New staff and guest SSH sessions are blocked; Telnet is blocked.
  • Guest DNS and HTTP to the shared server work; guest ICMP and staff access do not.
  • Staff portal access still works.
  • Rule order, interface direction, and enabled VTY lines match the policy.
  • The baseline and controlled .pkt checkpoints are saved separately.
